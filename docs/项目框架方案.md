# 大肥鱼狼人杀 · 项目框架方案

> 版本 v0.1（方案稿，未开工）
> 目标：网页狼人杀，**非人类玩家全部由 DeepSeek Harness 子代理扮演**，信息严格隔离，局末销毁、新局零继承。

---

## 0. 一句话架构

**纯前端网页 + 一个 Node 后端 + 每局一个 DSH runtime 子进程 + 每玩家一个 sessionId。**

游戏规则引擎是后端里一个**不依赖 DSH 的纯状态机**；DSH 只负责「把一个座位的可见信息变成一次行动」。两者用 `act` 工具协议对接。

---

## 1. 为什么这么接（已验证结论）

| 候选方案 | 结论 |
| --- | --- |
| 直接调 DeepSeek HTTP API + 自己写提示词 | 放弃：等于不用 Harness，而用户的原始诉求就是「接 DSH」 |
| 复用 1518 端口 Web GUI 的 Host API | 放弃：那是 GUI 内部 Typert RPC（每次调用要带 peer、有 remoteAccess 判定），耦合内部契约 |
| headless 一次性任务 | 放弃：进程只活一次，做不了多轮对局 |
| **sdk-minimal profile + stdio JSON-RPC** | **采用**：一个进程内多 session、天然上下文隔离、可复用桌面端已登录账号、无需 API Key |

已实测确认的能力（详见 [技术验证报告](技术验证报告.md)）：

- 一个 runtime 进程内 12 个 session 并行一轮 **2213ms**，冷启动到 `initialize` 返回 **1.3s**。
- 每个 session 只知道自己的身份，能独立记忆自己的历史 → **sessionId 就是隔离边界**。
- 可以给单个 agent 注册专属工具（`act`）和专属人格（systemPrompt section）。
- 关掉持久化插件后，同 sessionId 换进程旧上下文完全消失，且**不写任何磁盘文件**。

## 2. 总体架构

```
┌──────────────────────────────────────────────┐
│ 浏览器（纯 HTML/CSS/JS，无框架）              │
│  大厅：名称 + 头像 + 模式选择                  │
│  对局：座位圈、发言流、投票面板、身份卡         │
└───────────────┬──────────────────────────────┘
                │ HTTP (REST) + WebSocket
┌───────────────▼──────────────────────────────┐
│ Node 后端（server/）                          │
│                                              │
│  ┌────────────────┐   ┌───────────────────┐  │
│  │ 对局编排器       │──▶│ DSH runtime 客户端 │  │
│  │ match.mjs       │◀──│ runtime.mjs       │  │
│  └───────┬────────┘   └─────────┬─────────┘  │
│          │                      │ stdio JSON-RPC
│  ┌───────▼────────┐   ┌─────────▼─────────┐  │
│  │ 规则引擎        │   │ 子进程：DSH runtime│  │
│  │ engine.mjs      │   │ 6/9/12 个 session  │  │
│  │ view.mjs 信息投影│   │ 每个 = 一个玩家    │  │
│  └────────────────┘   └───────────────────┘  │
└──────────────────────────────────────────────┘
```

**关键分层原则**：规则引擎不认识 DSH，DSH 不认识狼人杀规则。中间只靠两个契约对接：
1. `view(seat)` → 该座位此刻能看到的一段文本。
2. `act` 工具 → 该座位提交的一次结构化行动。

这样规则引擎可以完全离线单测，DSH 部分坏了也不影响规则正确性。

## 3. 一局的生命周期

```
用户点「开始」
   │
   ├─▶ 分配身份（服务端随机，前端永不可见其他人的牌）
   ├─▶ 新建临时 DSH_HOME（工作区内 .runtime/match-<id>/）
   ├─▶ 启动 DSH 子进程（--profile sdk-minimal --patch <本局 patch>）
   ├─▶ initialize（校验 provider/model，约 1.3s）
   │
   ├─▶ 循环：夜晚 → 白天
   │      ├─ 每个需要行动的座位并行 session/prompt
   │      ├─ 收集 act 工具调用 → 结算
   │      └─ 把「公开事件」广播给所有座位 + 前端
   │
   ├─▶ 分出胜负
   │
   └─▶ 收尾：shutdown → 杀进程 → 删临时 DSH_HOME
          （所有子代理上下文随进程蒸发，磁盘零残留）
```

一局 6 人、约 5–8 个阶段，实测单阶段 3–7s → **整局 1–2 分钟**，符合陪玩体感。

## 4. 规则引擎设计

### 4.1 角色配置（`server/game/rules.mjs`）

| 模式 | 狼人 | 村民 | 预言家 | 女巫 | 猎人 | 守卫 |
| --- | --- | --- | --- | --- | --- | --- |
| 6 人 | 2 | 2 | 1 | 1 | – | – |
| 9 人 | 3 | 3 | 1 | 1 | 1 | – |
| 12 人 | 4 | 4 | 1 | 1 | 1 | 1 |

用户固定占一个座位（默认 1 号），身份随机。

### 4.2 状态结构

```js
match = {
  id, mode, seats: 6|9|12,
  players: [{ seat, name, avatar, role, alive, isHuman }],
  phase: 'night' | 'day' | 'vote' | 'ended',
  day: 1,
  nightActions: { wolfTarget, guardTarget, witchSave, witchPoison, seerCheck },
  votes: { [voterSeat]: targetSeat },
  publicLog: [{ day, phase, type, text }],   // 所有人可见
  seatKnowledge: { [seat]: [...] },          // 只有该座位可见的私有信息
  winner: null | 'werewolves' | 'villagers',
}
```

**信息隔离的物理保证**：私有信息只存在于 `seatKnowledge[seat]`，`view(seat)` 只读自己那一份 + `publicLog`。子代理之间没有任何共享通道（不同 sessionId），所以泄漏面为零。

### 4.3 阶段流程

**夜晚**（顺序固定，避免信息交叉）：

1. **守卫**守护一人（不可连续两晚守同一人，可守自己）→ `act{kind:'guard_protect', target}`
2. **狼人**共同刀一人 → 每个狼各投一票 `act{kind:'wolf_kill', target}`，取多数；平票取最早提交
3. **女巫**：知道「今晚被刀的是 X」，可选救（一瓶）/ 可选毒（一瓶）→ `act{kind:'witch_save'|'witch_poison'|'pass', target}`
4. **预言家**验一人 → `act{kind:'seer_check', target}`，结果只回给预言家

结算顺序：守卫护盾挡刀 → 女巫救 → 女巫毒 → 得出死亡名单。

**白天**：

1. 公布昨夜死讯（不公布死因）
2. 从「第一天随机 / 之后从死者下一位」开始，**依次**发言（不是并行：后发者要能引用前发者原话）
3. 全员投票 `act{kind:'vote', target}`，平票则平票者各补一句发言后重投一次，再平票则无人出局
4. 被放逐者若是猎人 → `act{kind:'hunter_shoot', target}`（被毒死时不能开枪）
5. 检查胜负

**胜负**：狼人全灭 → 好人胜；存活狼人数 ≥ 存活好人数 → 狼胜（可配置为屠边规则）。

### 4.4 为什么发言要串行、行动要并行

- 夜晚行动彼此不可见 → **并行**，一轮 2–7s。
- 白天发言必须有序且后发者能看到前文 → **串行**，6 人一轮约 6×2s ≈ 12s。
- 投票可以**并行**（互相不可见）。

这个取舍直接决定一局时长，写进代码注释里。

## 5. 信息投影（`server/game/view.mjs`）

这是整个项目**最需要小心**的一段代码。核心函数只有一个：

```js
view(match, seat) -> string   // 该座位此刻应该看到的全部文本
```

输出示例（6 号座位，村民）：

```
【对局】6人局 · 第2天白天
【你的身份】6号 · 村民
【存活】1,3,4,5,6（2号昨夜死亡）
【昨夜】2号死亡
【公开记录】
  第1天 · 发言 · 1号：我是村民，我觉得3号发言太急了。
  第1天 · 发言 · 3号：我是预言家，昨晚验1号是好人。
  第1天 · 投票 · 放逐2号（得票4）
【现在】轮到你发言，请调用 act 提交 kind=speak。
```

规则：
- 只拼接 `publicLog` + `seatKnowledge[seat]`。
- 狼人额外拼「你的队友是 X 号」。
- 预言家拼历史验人结果。
- 女巫拼「解药剩余 1 / 毒药剩余 1」。
- **绝不**把 `nightActions` 原文、其他座位的身份、其他座位的私有信息拼进去。

配一个自检：`assertNoLeak(match, seat, text)` —— 若文本里出现其他存活座位被分配的**狼人身份关键词**或他人验人结果，直接抛错。开发期常开。

### 6.2 每个座位的专属配置（插件内）

插件 `server/dsh/werewolf-plugin.mjs` 在 `agent/created` 时给该 agent 做两件事：

```js
ctx.on('agent/created', ({ agent }) => {
  const seat = seatOf(agent.id)          // sessionId 约定为 'm<matchId>-p<seat>'
  if (!seat) return

  // 1) 人格 + 身份
  agent.ctx.systemPrompt.section({
    name: 'werewolf-seat',
    order: 50,
    text: SEAT_PERSONA[seat].identityText,
  })

  // 2) 专属行动工具
  agent.ctx.tools.register({
    name: 'act',
    description: '提交你本回合唯一的行动。所有行动必须通过它提交，不要在正文里说话。',
    parameters: { /* 见 6.3 */ },
    output: {
      schema: { type:'object', properties:{ ok:{type:'boolean'}, echo:{type:'string'} }, required:['ok','echo'], additionalProperties:false },
      render: (args, v) => [{ type:'text', text: String(v && v.echo) }],
    },
    async execute(args) { return bridge.submit(seat, args) },
  })
}, { global: true })
```

踩坑备忘（都已实测）：
- `ctx.get('tools')` 的服务键就是 `tools`；`systemPrompt` 就是 `systemPrompt`。
- `agent/created` 回调参数是 `{ agent, source }`，**必须解构**，否则 `agent` 是 undefined。
- `tools.register` **必须带 `output.schema` + `output.render`**。
- 不要监听 `ready` 事件（不存在）。

### 6.3 `act` 工具契约

```jsonc
{
  "kind": "speak" | "vote" | "wolf_kill" | "seer_check" |
          "witch_save" | "witch_poison" | "guard_protect" |
          "hunter_shoot" | "pass",
  "target": "3",          // 座位号字符串，需要目标的 kind 必填
  "text": "我是村民……"     // speak 必填，其他忽略
}
```

服务端校验（`execute` 里做）：
- 该座位此刻是否真的需要行动 → 否则返回 `{ok:false, echo:'现在不是你的行动阶段'}`。
- `kind` 是否在当前阶段白名单内 → 否则回 `{ok:false, echo:'当前阶段只能 speak'}`。
- `target` 是否存活、是否合法（狼不能刀狼、女巫不能毒自己、预言家不能验自己）→ 否则回错误说明。

**返回 `ok:false` 让模型自我修正**，比在服务端静默丢弃好得多 —— 实测模型看到错误会立刻重试正确参数。

### 6.4 一轮行动的编排（`server/session/match.mjs`）

```js
async function runPhase(match, phase, seatsNeedingAction) {
  const pending = new Map()          // seat -> act
  const waiters = seatsNeedingAction.map(seat => new Promise(resolve => {
    pending.set(seat, { resolve, timer: setTimeout(() => resolve(null), PHASE_TIMEOUT) })
  }))

  await Promise.all(seatsNeedingAction.map(seat =>
    rpc.request('session/prompt', {
      sessionId: 'm' + match.id + '-p' + seat,
      contentBlocks: [{ type: 'text', text: view(match, seat) }],
    })
  ))

  await Promise.all(seatsNeedingAction.map(seat =>
    rpc.request('session/wait', { sessionId: 'm' + match.id + '-p' + seat })
  ))

  // 缺行动的座位：补一句「你尚未提交，请立即调用 act」，最多重试 2 次
  // 仍缺 → 兜底（pass / 随机合法目标），并记录到 match.warnings
  return settle(pending)
}
```

关键点：
- `session/prompt` 返回的 `messageId` **只是入队凭据**，不代表回合结束。
- 回合结束信号是 `session.event` 里的 `turn/end`（`reason.kind === 'completed'`），或者直接用 `session/wait`。
- **协议没有 prompt-cancel、也没有 per-session close** → 卡住的回合只能靠 `PHASE_TIMEOUT` 兜底，绝不能指望中途打断。

## 7. 前端设计（`web/`）

纯 HTML + CSS + 原生 JS，零构建步骤。

### 7.1 页面

| 页面 | 内容 |
| --- | --- |
| 大厅 `index.html` | 名称输入、头像选择（内置 12 张预设头像 + 上传本地图片转 dataURL）、模式选择 6/9/12、开始按钮 |
| 对局 `game.html` | 座位圈、当前阶段、公开发言流、投票面板、我的身份卡、夜间行动面板 |
| 结算 | 全场身份揭示、MVP、再来一局（**开新局 = 新进程，不继承任何上下文**） |

### 7.2 玩家档案持久化

`localStorage` 存 `{ name, avatar }`，跨局保留；头像上传用 `FileReader` 转 dataURL（限制 256KB），**不上传服务器磁盘**，只随对局请求传给后端、在座位圈里渲染。

### 7.3 通信

- `POST /api/match` → `{ matchId }`
- `GET  /api/match/:id` → 完整状态（前端拿到的状态是**已按你座位过滤**的）
- `WS   /ws/:matchId` → 推送 `phase-changed / speak / vote-result / death / game-over`
- `POST /api/match/:id/action` → 用户自己的行动

**前端永远拿不到其他人的身份** —— 后端返回给浏览器的状态走同一个 `view()` 投影逻辑，只是输出 JSON 而不是文本。

## 9. 关键技术风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 模型不调用 `act`，只在正文里说话 | 状态机拿不到行动 | ①系统提示强约束「必须调用 act」②`turn/end` 后检测缺失 → 补 prompt 重试 2 次 ③仍缺则兜底 pass 并记 warning |
| 单个座位卡住 | 整局阻塞 | `PHASE_TIMEOUT`（夜晚 25s / 发言 20s / 投票 20s）→ 兜底行动 |
| 上下文泄漏 | 游戏失去意义 | `view()` 单点出口 + `assertNoLeak()` 开发期断言 + 单测覆盖「村民视角不含狼队友」 |
| 一局时间长 | 体感差 | 发言串行其余并行；`reasoningEffort: 'low'`；12 人局实测单阶段 2.2s |
| runtime 进程崩溃 | 整局丢失 | 编排器捕获进程退出 → 前端提示「本局中断」，用户可重开（重开就是新进程，天然干净） |
| 拿不到 token 用量 | 无法计费/限流 | `request/context` 只有 114 字节、无 usage 字段；改为按「字符数 × 阶段数」自估，或直接不做计费 |
| 无 per-session close | 局末释放粒度只能是进程 | 一局一进程，`shutdown` + kill + 删临时目录 |

## 10. 实施里程碑

| 阶段 | 交付 | 验证方式 |
| --- | --- | --- |
| **M1 规则引擎** | `rules/engine/view` + 单测 | `node --test` 全绿；不需要 DSH，可离线跑完整局（所有座位随机行动） |
| **M2 DSH 桥** | `runtime.mjs` + `werewolf-plugin.mjs` | 起进程、6 个 session、`act` 工具能收到结构化参数 |
| **M3 编排器** | `match.mjs` 跑通 6 人整局 | 后端日志能输出完整一局战报，无需前端 |
| **M4 前端** | 大厅 + 对局页 + 头像自定义 | 浏览器里真人打一局 6 人 |
| **M5 扩模式** | 9 / 12 人（猎人、守卫技能） | 各打一局 |
| **M6 打磨** | 人格差异化、结算页、断线重连、日志回放 | — |

每阶段结束都能独立跑，不存在「全做完才知道行不行」。

## 11. 已定决策（本方案的选择，附理由）

1. **不建自定义 profile，直接用 `sdk-minimal` + 每局 `--patch`** —— 少一层配置漂移；patch 内容由代码生成，可随版本演进。
2. **一局一个 runtime 进程** —— 协议没有 per-session close，只有进程级释放能满足「局末销毁、不继承上下文」。
3. **关掉 `sessions` 持久化** —— 实测不落盘、不残留，且避免 `session already exists` 冲突。
4. **`act` 工具驱动状态机，不解析自由文本** —— 结构化参数零歧义，规则引擎不用写自然语言解析。
5. **白天发言串行、其余并行** —— 发言需要上下文引用，行动不需要。
6. **零依赖后端**（Node 内置 http + 手写 WebSocket 帧处理，或只引入 `ws` 单包）—— 降低部署复杂度。
7. **前端零构建** —— 用户明确要「网页 html 做前端」，直接静态文件即可，改一行刷新就见效。
